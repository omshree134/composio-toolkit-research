# Pylon MCP

Expose Pylon data to AI tools and assistants via Model Context Protocol.

## Pylon MCP Server

The Pylon MCP Server exposes Pylon data to AI tools that support the Model Context Protocol (e.g. Claude, ChatGPT, Cursor). AI tools authenticate with OAuth or an API token and can read and update issues, accounts, contacts, knowledge base articles, tasks and projects, triggers, and more within the authenticated identity's permissions.

- Server URL (US): `https://mcp.usepylon.com`
- Server URL (EU): `https://mcp.eu.usepylon.com`
- Auth: OAuth 2.0 or an API token. Actions are performed as the signed-in user or the token's identity, with that identity's current role and permissions.
- Transport: Streamable HTTP (stateless; no server-side sessions).

### Setup in Pylon

Open Settings > AI Controls > MCP Server in Pylon. Copy your workspace's regional MCP URL from Installation and use it in your AI tool. For client-specific instructions, see connecting to the Pylon MCP Server.

### Authentication

Both methods use the same regional MCP URL. Choose the method your client supports.

#### OAuth

Use OAuth with AI tools that offer an interactive connection flow. Add the regional MCP URL to your client, then sign in to Pylon when prompted. MCP requests run as the user who authorizes the connection.

#### API token

Use an existing API token for headless workers, scripts, or MCP clients that support custom authorization headers. You don't need a separate MCP token or an interactive sign-in.

1. Create or choose an API token.
2. Configure your client with your workspace's regional MCP URL.
3. Include this header on every MCP request:

Replace `<API_TOKEN>` with the token value. Use `https://mcp.usepylon.com` for US workspaces and `https://mcp.eu.usepylon.com` for EU workspaces; the token must belong to the same region.

A token with its own identity uses the role assigned to that identity. A token linked to a teammate or bot uses that user's current role and permissions. The identity must have MCP Access, and each tool still requires the permissions for its operation. Any IP allowlist configured on the token also applies to MCP requests.

Some clients only support OAuth connections. Use their OAuth flow if they don't let you configure an authorization header.

### What you can do with MCP today

The authenticated user or token identity needs the MCP Access permission to connect. The standard Member and Admin roles include this permission. Each tool also requires the permissions for its operation. Access follows the same scoping as the Pylon dashboard — the MCP cannot return data that the authenticated user cannot already see, or perform writes that the authenticated user cannot already write in the UI.

Some tools also require a plan feature, noted in their section. Rate limits apply per tool, elaborated below.

Use the tool names below when configuring your AI client. Your client discovers the input schema for each tool through MCP; available tools depend on your workspace, plan, and permissions.

For a tool whose input schema includes `arguments`, put its required and optional fields inside that object. For example:

Use the schema returned by your client for the exact fields. Writes apply immediately; confirm the intended change before calling them. If the outcome of a write is unknown, check the record before retrying.

Write tools reject arguments they don't recognize instead of ignoring them; the error names the unknown arguments and lists the valid ones. A different casing of a field name, such as `customerPortalTitle` for `customer_portal_title`, is accepted, and tools with a `state` field also accept `status`. Supply each field only once: sending a field under both its name and an alias returns an error.

`search_issues` can return each issue's messages with `include_messages`. On large pages, `max_messages_per_issue` keeps only each issue's latest messages (`messages_truncated` is set when older ones were dropped), and `max_message_chars` cuts each message body to that many characters (`body_truncated` is set). Set `include_total` to also get the exact number of matching issues you can read across all pages; it costs an extra query, so use it when sizing work rather than on every page.

`get_issue_messages`, and `get_issue` with `include_messages=true`, list each message's attachments with an `index`, a file name, and a download URL. Images aren't downloaded by default; set `include_images` to `true` when your AI tool needs to look at them. Images hosted in Pylon (PNG, JPEG, GIF, and WebP) are returned as image content, up to 5 images per call, 5 MB each and 10 MB in total, and images that can't be attached are noted in the response. To read a single attachment, call `get_message_attachment` with the `issue`, `message_id`, and `attachment_index` from a message read. Images come back as image content with the same limits.

For UTF-8 text attachments hosted by Pylon, `get_message_attachment` returns the text in a content block and reports the read status in `read`. Supported extensions are CSV, TSV, JSON, JSONL, NDJSON, TXT, LOG, MD, YAML, YML, XML, SQL, INI, CONF, and TOML. Files can be up to 5 MiB, with up to 64 KiB of text per response.

- `complete`: no more text remains.
- `partial`: pass `read.next_cursor` as `cursor` with the same `issue`, `message_id`, and `attachment_index` to read the next page. Access is checked on every call. If the file changes, restart without a cursor.
- `unsupported`: use the download link for other formats, external files, non-UTF-8 content, or oversized files.
- `unavailable`: the download failed. Retry or use the download link.

Tools that act on a single issue accept its ID or its number, as a string or an integer, and a leading `#` is fine. Common alternative argument names such as `issue_id`, `issue_number`, or `ticket_id` also work; if you send more than one and they point to different issues, the call fails before anything changes.

`update_issue` can also set `customer_portal_title`, the title customers see in the customer portal, and `customer_portal_visible`, which shows or hides the issue in the customer portal. Omit either to leave it unchanged. `search_issues` results include `customer_portal_title`, and `get_issue` returns `customer_portal_visible`.

`update_issues` changes only the fields you provide. Issues that don't exist or that you can't update are listed in `skipped_issues` instead of failing the call. Tags replace the issue's tags by default; set `tags_apply_mode` to `append_only` to add tags or `remove_only` to remove them. Use `update_issue` for per-issue changes such as priority or custom fields.

`update_issue` and `update_account` accept the same `tags_apply_mode` for `tags`: `replace` (the default), `append_only`, or `remove_only`. Adding or removing leaves other tags in place and is safe to retry. Setting `tags_apply_mode` requires a tag list, and omitting `tags` leaves tags unchanged.

#### Accounts

#### Account Notes

Requires Account Intelligence and permission to read or update the account.

| Tool | Read / Write | Description |
| --- | --- | --- |
| `get_account_notes` | Read | List the notes in an account's Notes block, newest first |
| `save_account_note` | Write | Create a timestamped account note or edit its title or HTML body |

Both tools work on one Notes block in an account notebook. To get its ID, hover over the Notes block in Pylon, open Notes block actions, and select Copy block ID. Pass it as `widget_id`.

Use `get_account_notes` with `account_id` and `widget_id` to list notes, up to 20 per page. When `has_next_page` is true, pass the returned `cursor` to fetch older notes. Each note includes its `id`.

Use `save_account_note` without `note_id` to create a note; `account_id`, `widget_id`, and nonempty `content_html` are required.

To edit a note, supply a nonempty `note_id` and `title` and/or `content_html`. Use `get_account_notes` to find note IDs. Omit either field to preserve it; send an empty `title` to clear the title. An empty `content_html` is rejected, and HTML is sanitized. `account_id` and `widget_id` apply only when creating. An explicitly empty `note_id` is rejected; omit it to create.

#### Contacts, Users & Teams

For `save_contact`, omit `contact_id` to create a contact; `name` and `account_id` are required, and `email` is optional. New contacts don't get customer portal access or an invite. To update, read the contact with `get_contact`, then supply a nonempty `contact_id` and only the fields to change. `email` is create-only. Contacts with customer portal access cannot be moved to another account through this tool.

To merge duplicate contacts, supply only `contact_id` and `merge_into_contact_id`; merging needs permission to delete contacts. The contact in `contact_id` is merged into the other one and then permanently deleted, and the merge can't be undone. Its issues, emails, and phone numbers move to the surviving contact. Both contacts must be on the same account, unless `contact_id` has no account, in which case it moves to the surviving contact's account. If that contact can log in to the customer portal, merge it in Pylon instead.

Team reads require permission to view team settings; `save_team` requires permission to edit them. Omit `team_id` to create a team with `name` and `icon`, or supply a nonempty `team_id` to update it. Read `get_team` before changing membership. Removing a teammate also deletes schedule blocks they own in that team. Team changes apply in order; if a later change fails, earlier changes remain applied.

`get_article` doesn't download images by default. Set `include_images` to `true` when your AI tool needs to look at an article's images, for example to check screenshots or alt text. Images hosted in Pylon are returned as image content along with each image's URL and alt text; images hosted elsewhere stay as URLs in the article text. To tag an article, pass `tag_ids` to `update_article_settings`. By default the list replaces the article's current tags, and an empty list removes every tag. To edit a collection, supply its `collection_id` and only the `title`, `description`, or `slug` to change; send an empty `description` to clear it. Pass `parent_collection_id` to move the collection, along with its articles and sub-collections, under another collection in the same knowledge base. Use `list_knowledge_bases` and `list_collections` to find IDs. Change a collection's visibility and AI agent access in Pylon.

Requires the Feature Requests plan feature.

| Tool | Read / Write | Description |
| --- | --- | --- |
| `search_feature_requests` | Read | Search feature requests by status and other filters |
| `get_feature_request` | Read | Fetch a feature request, including its evidence and the accounts that can see it in the customer portal |
| `get_feature_request_statuses` | Read | List the feature request statuses configured for your org |
| `save_feature_request` | Write | Create a feature request with optional initial evidence, or update its title, description, status, or custom fields |
| `add_evidence_to_feature_request` | Write | Record that a customer asked for an existing feature request, linking the issue or account |
| `merge_feature_requests` | Write | Merge duplicate feature requests into one; evidence and linked tickets move over and the duplicates are archived |
| `remove_feature_request_evidence` | Write | Unlink evidence that doesn't support a feature request, such as an issue that asked for something different |
| `set_feature_request_portal_visibility` | Write | Show or hide feature requests in the customer portal for specific accounts |
| `delete_feature_request` | Write | Permanently delete a feature request |

For `save_feature_request`, omit `feature_request_id` to create a request with a nonempty `title` and `description`. Search first; if a matching request exists, use `add_evidence_to_feature_request` instead. `issue_id`, `account_id`, and `evidence_summary` apply only when creating.

Supply a nonempty `feature_request_id` to update only the provided fields. `request_status` and `custom_fields` apply only when updating; use `get_feature_request_statuses` to find valid statuses. Results contain the new request under `created` or the updated request under `updated`.

`remove_feature_request_evidence` takes a `feature_request_id` and up to 50 evidence IDs from `get_feature_request`; every ID must belong to that request. The source issue, call, or survey response isn't deleted. Accounts left without evidence on the request can no longer see it in the customer portal.

`set_feature_request_portal_visibility` applies to every pair of the `feature_request_ids` and `account_ids` you pass, so you can share one request with many accounts or many requests with one account, up to 500 pairs per call. A request can only be shown to accounts that asked for it, meaning they have evidence on it. Changes are all or nothing: if one pair fails, none are applied. The result lists which accounts can see each request afterward.

`delete_feature_request` permanently deletes the request along with its evidence links, linked product issues, and portal visibility, and can't be undone. To combine duplicates, use `merge_feature_requests` so the evidence is kept. To retire a stale or rejected request, archive it by updating its status with `save_feature_request`. AI tools are instructed to confirm with you before deleting.

#### Triggers

New triggers are created disabled so you can review them in Pylon before turning them on.

Use `validate_trigger` before saving. `save_trigger` supports custom trigger groups and flat branches with compatible actions, delays, and conditions, including recurring schedule kickoffs. Configure default or special groups, phone/IVR triggers, nested branches, and background-agent investigations in Pylon instead. Updating a trigger replaces its editable configuration while preserving its group and enabled state.

To change only which records a trigger acts on, use `update_trigger_conditions`. Pass `branch_conditions`, mapping top-level branch IDs from `get_trigger` to new filters from `build_filter`; only those branches' conditions are replaced. Kickoffs, actions, branch and step IDs, group, title, description, and enabled state are kept, so this also works on triggers in default or special groups and on triggers with background-agent actions. To add an exclusion, combine it with the branch's complete existing filter, including any OR group. Updating conditions doesn't run the trigger.

To build a recurring schedule, call `describe_trigger_kickoff` with `kickoff_type` `recurring_schedule` and the `object_type` the schedule runs on (for example `issue` or `account`). It returns the schedule fields and the actions that object supports; `get_trigger_examples` includes a weekday schedule example. Every enabled branch of a scheduled trigger needs a filter that selects which records it acts on. `build_filter` can't build meeting filters, so reuse an existing meeting filter from `get_trigger` or set it up in Pylon. To change an existing schedule, start from its `get_trigger` configuration. If a schedule uses recurrence settings that `save_trigger` can't represent, the update is rejected and the trigger is left unchanged; edit it in Pylon instead.

#### Macros

Discover saved macros, create or edit their message text, and delete them. Reading macro details requires permission to view macro settings; saving and deleting require permission to edit macro settings and the macro itself.

| Tool | Read / Write | Description |
| --- | --- | --- |
| `list_macros` | Read | List visible macro summaries and groups, with optional name search and group filtering |
| `get_macro` | Read | Read stored HTML, text type, visibility, configured action types, and attachment summaries |
| `save_macro` | Write | Create a text-only macro or edit an existing macro's name, message text, or text type |
| `delete_macro` | Write | Permanently delete a macro, including its actions and attachments |
| `get_macro_groups` | Read | Get all macro groups |

`list_macros` accepts `query`, `macro_group_id`, `limit` (default 25, maximum 100), and `cursor`. Continue with the returned cursor and the same filters when `has_next_page` is true.

To create a macro, provide `name`, `macro_group_id` from `list_macros`, and either Markdown `text` or HTML `text_html`. New macros are organization-visible and default to the `reply` text type; `note` and `email` are also supported.

To edit a macro, first call `get_macro`, then supply its `macro_id` and only the fields you want to change. Use `text_html` when editing returned HTML to preserve rich formatting and template metadata. `text` and `text_html` are mutually exclusive and both are sanitized. Explicitly empty content, or content with neither text nor a safe image after sanitization, is rejected. Omit both to preserve existing message text.

Existing actions, conditions, visibility, editor permissions, group, and attachments are preserved. Change those settings or remove files in Pylon. Attachment summaries are read-only and limited to 100 entries; check `attachment_count` and `has_more_attachments` for additional files. These tools do not execute macros, resolve template variables against an issue, or send messages.

`delete_macro` takes a `macro_id` from `list_macros`. Deleting a macro can't be undone.
